          A YANG Data Model for BGP-LS Segment Routing Policy
            draft-aravind-lsvr-bgp-ls-sr-policy-yang-latest

Abstract

   This document defines a YANG 1.1 data model for the Segment Routing
   (SR) Policy Candidate Path Network Layer Reachability Information
   (NLRI) and its associated BGP Link-State (BGP-LS) attributes.  The
   model augments the operational BGP-LS Link-State Database defined by
   the BGP-LS YANG model with the protocol elements specified in RFC
   9857.

1.  Introduction

   [RFC9552] describes a mechanism by which Link-State (LS) and Traffic
   Engineering (TE) information can be collected and distributed using
   the Border Gateway Protocol (BGP).  [RFC9857] extends that mechanism
   with the SR Policy Candidate Path NLRI and BGP-LS Attribute Type-
   Length-Values (TLVs) that advertise the operational state of an SR
   Policy at candidate-path granularity.  The advertised information
   includes the Binding Segment Identifier (SID), candidate-path state
   and names, constraints, and the segment lists associated with the
   candidate path.

   [I-D.ietf-lsvr-bgp-ls-yang] defines a [RFC7950] YANG 1.1 data model
   for BGP-LS, BGP-LS-VPN, and BGP-LS-SPF under the routing management
   model defined in [RFC8349].  It includes a read-only Link-State
   Database (LSDB) for the Node, Link, Prefix, and SRv6 SID NLRIs
   received using BGP-LS.  This document defines the ietf-bgp-ls-sr-
   policy module, which augments that LSDB with a read-only
   representation of the SR Policy Candidate Path NLRI and its
   associated attributes defined in [RFC9857].

2.  Terminology

   This document uses the terminology defined in [RFC9256], [RFC9552],
   and [RFC9857].  The following terms are used throughout this
   document:

   Candidate path (CP):  A path that is associated with an SR Policy.
      An SR Policy can have more than one candidate path, but only one
      candidate path is active at a time, as described in [RFC9256].

   Headend:  The node at which an SR Policy is instantiated and where
      traffic is steered onto the policy, as described in [RFC9256].

   Segment list:  An ordered list of segments that describes a path
      through the SR domain, as described in [RFC9256].

4.  YANG Model

4.1.  BGP-LS SR Policy YANG Model

   The ietf-bgp-ls-sr-policy module augments the operational BGP-LS LSDB
   defined by [I-D.ietf-lsvr-bgp-ls-yang].  It does not configure SR
   Policies and does not change BGP-LS protocol behavior.  The module
   augments the link-state database and does not augment the separate
   link-state-spf database because [RFC9857] defines the SR Policy
   Candidate Path NLRI for BGP-LS.

   The sr-pol-cp container is a sibling of the nodes, links, prefixes,
   srv6-sids, and unknowns containers in an LSDB instance.  The
   container is present when the Protocol-ID is Segment Routing (9), as
   assigned by [RFC9857].

   Each candidate-path entry represents one SR Policy Candidate Path
   NLRI.  The key contains the fields from the Local Node Descriptors
   TLV and the mandatory SR Policy Candidate Path Descriptor TLV.  At
   least one IPv4 or IPv6 Router-ID is required to identify the SR
   Policy headend.  Optional node descriptors use their unspecified
   values when they are not present so that the list has a fixed YANG
   key.

   The attributes container represents the BGP-LS Attribute associated
   with the NLRI.  It includes the SR and SRv6 Binding SID TLVs,
   candidate-path state and names, constraints, segment lists, metrics,
   and attributes that are not recognized by the implementation.
   Segment lists and segments are ordered-by user to preserve their
   received order.  Their index leaves are zero-based positional keys.
   The optional Segment List Identifier defined in Section 5.7.4 of
   [RFC9857] is represented separately and is not used as the list key.

   Segment descriptor Types A through K from Section 5.7.1.1 of
   [RFC9857] are represented by separate cases.  The module reuses the
   SRv6 SID attribute and unknown attribute groupings from the BGP-LS
   LSDB model.  These groupings include the SRv6 Endpoint Behavior and
   SID Structure attributes defined in [RFC9514].  Bandwidth is
   represented in bytes per second, consistent with the encoding
   specified by [RFC9857].

   The module imports the BGP model defined by [I-D.ietf-idr-bgp-model]
   and the BGP-LS and LSDB modules defined by
   [I-D.ietf-lsvr-bgp-ls-yang].

6.  Security Considerations

   The YANG module specified in this document defines a schema for data
   that is designed to be accessed through network management protocols
   such as NETCONF [RFC6241] or RESTCONF [RFC8040].  The lowest NETCONF
   layer is the secure transport layer, and the mandatory-to-implement
   secure transport is Secure Shell (SSH) [RFC6242].  The lowest
   RESTCONF layer is HTTPS, and TLS [RFC9846] is mandatory to implement.

   The Network Configuration Access Control Model (NACM) [RFC8341]
   provides the means to restrict access for particular users to a
   preconfigured subset of all available protocol operations and
   content.

   All data nodes introduced by the ietf-bgp-ls-sr-policy module are
   read-only.  The sr-pol-cp subtree contains headend and endpoint
   addresses, Binding SIDs, complete segment lists, path constraints,
   bandwidth, and disjointness relationships.  Unauthorized read access
   to this information may disclose network topology, traffic-
   engineering intent, and protection strategy.  Implementations MUST
   apply appropriate access controls to this subtree and SHOULD expose
   it only to trusted principals.

   The number of candidate paths, segment lists, segments, metrics, and
   unknown TLVs is controlled by received BGP-LS information.
   Implementations SHOULD apply the resource limits and malformed-TLV
   handling used for the underlying BGP-LS LSDB.  No RPC or action
   operations are defined by this document.

   The security considerations of [RFC9256], [RFC9552], [RFC9857],
   [I-D.ietf-idr-bgp-model], and [I-D.ietf-lsvr-bgp-ls-yang] also apply.

Appendix B.  Examples

   The following examples illustrate the BGP-LS LSDB populated with an
   SR-MPLS candidate path and an SRv6 candidate path.  The data is shown
   under the bgp-ls-topology container augmented into the link-state
   container at /rt:routing/rt:control-plane-protocols/rt:control-plane-
   protocol/ bgp:bgp/bgp:global/bgp:afi-safis/bgp:afi-safi/bgp-ls:link-
   state.  XML encoding follows [RFC7950].

B.1.  SR-MPLS Candidate Path

   The following example contains one SR-MPLS candidate path originated
   by local configuration.  The candidate path has an allocated Binding
   SID and one segment list containing an IPv4 Prefix SID.

    <control-plane-protocols>

         <bgp:afi-safi>

            <bgp-ls:instances>
             <bgp-ls:instance>
              <bgp-ls:vrf-name>default</bgp-ls:vrf-name>
              <bgp-ls:protocol>sr</bgp-ls:protocol>
              <bgp-ls:identifier>0</bgp-ls:identifier>
