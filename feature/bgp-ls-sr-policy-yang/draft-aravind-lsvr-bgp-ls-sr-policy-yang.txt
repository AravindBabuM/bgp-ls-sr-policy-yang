          A YANG Data Model for BGP-LS Segment Routing Policy
            draft-aravind-lsvr-bgp-ls-sr-policy-yang-latest

Abstract

   This document defines a YANG data model for the operational state of
   Segment Routing (SR) Policy candidate paths that are advertised using
   BGP - Link State (BGP-LS).  The model augments the read-only BGP-LS
   Link-State Database with the SR Policy Candidate Path Network Layer
   Reachability Information (NLRI) and the associated BGP-LS Attribute
   TLVs specified in RFC 9857.

1.  Introduction

   [RFC9552] specifies a mechanism by which Link-State (LS) and Traffic
   Engineering (TE) information is collected and distributed using the
   Border Gateway Protocol (BGP).  [RFC9857] extends that mechanism with
   the SR Policy Candidate Path NLRI (NLRI Type 5), the Segment Routing
   Protocol-ID (9), and a set of BGP-LS Attribute TLVs that report the
   operational state of an SR Policy [RFC9256] at candidate-path
   granularity.  The reported information includes the Binding Segment
   Identifier (BSID), the candidate-path state and names, path
   constraints, and the segment lists associated with the candidate
   path.

   [I-D.ietf-lsvr-bgp-ls-yang] defines a YANG 1.1 [RFC7950] data model
   for BGP-LS, BGP-LS-VPN, and BGP-LS-SPF as an extension of the BGP
   YANG data model [I-D.ietf-idr-bgp-model], which is itself
   instantiated under the routing management model [RFC8349].  That
   model includes a read-only Link-State Database (LSDB) for the Node,
   Link, Prefix, and SRv6 SID NLRIs received using BGP-LS, but it does
   not represent the SR Policy Candidate Path NLRI.

   This document defines the ietf-bgp-ls-sr-policy YANG module, which
   augments that LSDB with a read-only representation of the SR Policy
   Candidate Path NLRI and its associated BGP-LS Attribute TLVs.  The
   module does not configure SR Policies and does not alter BGP-LS
   protocol procedures.  The module conforms to the Network Management
   Datastore Architecture (NMDA) [RFC8342]; all data nodes defined by
   this document are reported in the operational state datastore.

2.2.  Terminology

   This document uses the terminology defined in [RFC9256], [RFC9552],
   and [RFC9857].  In addition, the following terms are used:

   Candidate path:  A path associated with an SR Policy, as defined in
      Section 2.2 of [RFC9256].  An SR Policy can have multiple
      candidate paths, of which at most one is active at any given time.

   Headend:  The node at which an SR Policy is instantiated and at which
      traffic is steered onto the SR Policy, as defined in [RFC9256].

   Segment list:  An ordered list of segments that describes a path
      through the SR domain, as defined in [RFC9256].  The term "SID
      list" is used interchangeably.

   Server:  The entity that implements the module defined in this
      document and exposes the BGP-LS LSDB through a network management
      protocol.

4.  Design of the Data Model

4.1.  Scope and Augmentation

   The ietf-bgp-ls-sr-policy module augments the operational BGP-LS LSDB
   defined by [I-D.ietf-lsvr-bgp-ls-yang].  The module augments only the
   link-state database.  The separate link-state-spf database is not
   augmented because [RFC9857] does not define the SR Policy Candidate
   Path NLRI for BGP-LS-SPF.

   The sr-pol-cp container is a sibling of the nodes, links, prefixes,
   srv6-sids, and unknowns containers in an LSDB instance.  A when
   statement restricts the container to LSDB instances whose protocol
   leaf is sr, which corresponds to the Segment Routing Protocol-ID (9)
   assigned by [RFC9857].  The NLRI Identifier field is represented by
   the identifier key of the enclosing LSDB instance.

4.2.  Candidate Path Identification

   Each entry in the candidate-path list represents one SR Policy
   Candidate Path NLRI.  The list key consists of the decoded fields of
   the Local Node Descriptors TLV followed by the fields of the
   mandatory SR Policy Candidate Path Descriptor TLV (TLV 554).
   Figure 2 shows the correspondence between the NLRI fields and the
   YANG data nodes.

    SR Policy Candidate Path NLRI     YANG data node
    (RFC 9857, Sections 3 and 4)
   +-------------------------------+
   | Protocol-ID (9)               |-> bgp-ls:instance/protocol
   +-------------------------------+
   | Identifier (64 bits)          |-> bgp-ls:instance/identifier
   +-------------------------------+
   | Local Node Descriptors (256)  |
   |   Autonomous System (512)     |-> candidate-path/as
   |   BGP Router-ID (516)         |-> candidate-path/bgp-router-id
   |   Confed. Member (517)        |-> candidate-path/member-as
   |   IPv4 Router-ID (1028)       |-> candidate-path/ipv4-router-id
   |   IPv6 Router-ID (1029)       |-> candidate-path/ipv6-router-id
   +-------------------------------+
   | SR Policy CP Descriptor (554) |
   |   Protocol-Origin             |-> candidate-path/protocol-origin
   |   Flags (E, O)                |-> candidate-path/descriptor-flags
   |   Endpoint                    |-> candidate-path/endpoint
   |   Policy Color                |-> candidate-path/color
   |   Originator ASN              |-> candidate-path/originator-as
   |   Originator Address          |-> candidate-path/originator-address
   |   Discriminator               |-> candidate-path/discriminator
   +-------------------------------+

               Figure 2: Mapping of NLRI Fields to List Keys

   YANG requires every key leaf to have a value.  [RFC9857] requires the
   Autonomous System (TLV 512) and BGP Router-ID (TLV 516) Node
   Descriptors when the headend is the BGP-LS Producer, but makes them
   optional when a PCE is the BGP-LS Producer.  The BGP Confederation
   Member (TLV 517) Node Descriptor is always optional, and at least one
   of the IPv4 Router-ID (TLV 1028) and IPv6 Router-ID (TLV 1029) Node
   Descriptors is required.  A server therefore MUST populate the key
   leaves as follows when the corresponding Node Descriptor TLV is
   absent from the NLRI:

   *  as and member-as: the value 0.

   *  bgp-router-id and ipv4-router-id: the IPv4 unspecified address
      (0.0.0.0).

   *  ipv6-router-id: the IPv6 unspecified address (::).

   A must statement enforces that at least one of ipv4-router-id and
   ipv6-router-id contains a specified address.

   [RFC9857] also permits other Node Descriptor TLVs defined in
   [RFC9552], such as the IGP Router-ID (TLV 515), to be included in the
   Local Node Descriptors TLV.  Such descriptors are not represented in
   the list key by this version of the module.

4.3.  Candidate Path Attributes

   The attributes container represents the BGP-LS Attribute associated
   with the NLRI.  Figure 3 shows the correspondence between the BGP-LS
   Attribute TLVs and sub-TLVs defined in [RFC9857] and [RFC9514] and
   the YANG data nodes defined under the attributes container.
   Indentation of the TLV code point indicates a sub-TLV of the
   preceding TLV.

   TLV   RFC 9857 element                Data node under attributes
   ----  ------------------------------  -------------------------------
   1201  SR Binding SID                  sr-binding-sid
   1212  SRv6 Binding SID                srv6-binding-sid
   1202  SR Candidate Path State         state
   1213  SR Policy Name                  policy-name
   1203  SR Candidate Path Name          candidate-path-name
   1204  SR Candidate Path Constraints   constraints
   1208    SR Affinity                   constraints/affinity
   1209    SR SRLG                       constraints/excluded-srlg
   1210    SR Bandwidth                  constraints/bandwidth
   1211    SR Disjoint Group             constraints/disjoint-group
   1214    SR Bidirectional Group        constraints/bidirectional-group
   1215    SR Metric                     constraints/metric
   1205  SR Segment List                 segment-list
   1206    SR Segment                    segment-list/segment
   1207    SR Segment List Metric        segment-list/metric
   1216    SR Segment List Bandwidth     segment-list/bandwidth
   1217    SR Segment List Identifier    segment-list/identifier
   1250  SRv6 Endpoint Behavior          .../srv6-sid-attributes
   1252  SRv6 SID Structure              .../srv6-sid-attributes
   ----  Unrecognized TLV or sub-TLV     unknown (at each level)

          Figure 3: Mapping of BGP-LS Attribute TLVs to Data Nodes

   The SRv6 Endpoint Behavior (TLV 1250) and SRv6 SID Structure (TLV
   1252) sub-TLVs apply to the srv6-binding-sid list entries and to the
   segment list entries.  These are represented by the SRv6 SID
   attribute grouping reused from [I-D.ietf-lsvr-bgp-ls-yang].

   The following rules apply to the representation of the BGP-LS
   Attribute:

   *  [RFC9857] specifies that only the first valid instance of certain
      TLVs and sub-TLVs is used when multiple instances are received.
      For such TLVs and sub-TLVs, the server MUST represent only the
      instance that is used according to [RFC9857].

   *  The SR Binding SID TLV (TLV 1201) is represented by the sr-
      binding-sid container.  The D-flag is represented by the
      srv6-dataplane bit of the flags leaf.  When the D-flag is clear,
      the server MUST report the Binding SID and Specified Binding SID
      fields in the binding-sid and specified-binding-sid leaves.  When
      the D-flag is set, the TLV uses the SRv6 encoding that is
      deprecated by Section 5.1 of [RFC9857], and the server MUST report
      these fields in the srv6-binding-sid and srv6-specified-binding-
      sid leaves.  In both cases, when either field is set to 0 (e.g.,
      because no Binding SID has been specified), the server MUST NOT
      report the corresponding leaf.

   *  When the Disjoint Group Identifier or Bidirectional Group
      Identifier field carries a 4-octet value, the server MUST report
      it in the group-id leaf.  When the field carries a PCEP
      ASSOCIATION Object [RFC8697], the server MUST report the object,
      as received, in the pcep-association-object leaf.

   *  Bandwidth values are encoded by [RFC9857] in bytes per second as
      IEEE 754 single-precision floating-point numbers [IEEE754].  The
      module represents bandwidth using the bandwidth-ieee-float32 type
      defined in [RFC8294], in bytes per second.  The server MUST report
      the received value without conversion or rounding.

   *  Each flag defined by [RFC9857] is represented by a bit of the same
      name in a YANG bits type.  The YANG bit positions match the bit
      numbering used in [RFC9857].  Bits that are undefined in [RFC9857]
      are ignored by a receiver and are not represented.

   *  A TLV or sub-TLV that is not recognized by the server SHOULD be
      reported in the unknown list of the enclosing level, using the
      unknown attribute grouping reused from
      [I-D.ietf-lsvr-bgp-ls-yang].

4.4.  Segment Lists and Segments

   Segment lists and segments are represented by lists that are ordered-
   by user so that the received order is preserved.  The server MUST
   assign the index key of a segment list according to the order in
   which the corresponding SR Segment List TLV appears in the BGP-LS
   Attribute, starting at 0.  The server MUST assign the index key of a
   segment according to the order in which the corresponding SR Segment
   sub-TLV appears in the SR Segment List TLV, starting at 0.  The
   optional Segment List Identifier defined in Section 5.7.4 of
   [RFC9857] is represented by the identifier leaf and is not used as
   the list key, because it is optional and is not required to be
   present for every segment list.  A segment list without any SR
   Segment sub-TLVs (e.g., a dynamic path that has not yet been
   computed) is represented by a segment-list entry without segment
   entries.

   Segment Descriptor Types A through K defined in Section 5.7.1.1 of
   [RFC9857] are represented by separate cases of the descriptor choice.
   The type leaf of a segment contains the Segment Type code point, and
   each case is constrained by a when statement to the corresponding
   code point.  The SID value is present only when the S-flag (sid-
   present) of the segment is set.  The Algorithm field of a Type A or
   Type B descriptor is meaningful only when the A-flag (algorithm-
   valid) of the segment is set.

6.  Security Considerations

   The YANG module specified in this document defines a schema for data
   that is designed to be accessed through network management protocols
   such as NETCONF [RFC6241] or RESTCONF [RFC8040].  The lowest NETCONF
   layer is the secure transport layer, and the mandatory-to-implement
   secure transport is Secure Shell (SSH) [RFC6242].  The lowest
   RESTCONF layer is HTTPS, and the mandatory-to-implement secure
   transport is TLS [RFC9846].

   The Network Configuration Access Control Model (NACM) [RFC8341]
   provides the means to restrict access for particular NETCONF or
   RESTCONF users to a preconfigured subset of all available NETCONF or
   RESTCONF protocol operations and content.

   There are no data nodes defined in this YANG module that are
   writable, creatable, or deletable (i.e., config true, which is the
   default).  The module therefore introduces no write-related
   vulnerabilities.

   Some of the readable data nodes in this YANG module may be considered
   sensitive or vulnerable in some network environments.  It is thus
   important to control read access (e.g., via get, get-data, or
   notification) to these data nodes.  These are the subtrees and data
   nodes and their sensitivity/vulnerability (the augmented path is
   abbreviated; the full path is shown in Appendix A):

   .../bgp-ls:instance/bgp-ls-sr-policy:sr-pol-cp:  This subtree
      contains headend, endpoint, and originator addresses, Binding
      SIDs, complete segment lists, path constraints, requested and
      allocated bandwidth, and disjointness and bidirectional
      associations.  Unauthorized read access to this information
      discloses network topology, traffic-engineering intent, and path-
      protection strategy, which [RFC9857] identifies as potentially
      commercially sensitive.  Such information can also assist an
      attacker in identifying critical nodes and links or in crafting
      packets that use valid SIDs.

   The content of this subtree is derived from BGP-LS information
   received from other speakers, and the number of candidate paths,
   segment lists, segments, metrics, and unknown TLVs is controlled by
   those speakers.  Implementations SHOULD apply to this subtree the
   same resource limits and malformed-TLV handling that apply to the
   underlying BGP-LS LSDB [RFC9552].

   This document defines no RPC or action operations.

   The security considerations of [RFC9256], [RFC9552], [RFC9857],
   [I-D.ietf-idr-bgp-model], and [I-D.ietf-lsvr-bgp-ls-yang] also apply.

B.1.  SR-MPLS Candidate Path

   The following example contains one SR-MPLS explicit candidate path
